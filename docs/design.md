## 1. 目的と前提

撮影した名刺写真を Gemini に渡して項目ごとに読み取り、社内で検索できる形で保存する。

| 項目 | 前提 |
| --- | --- |
| 利用者 | 社内 100 名程度。会社の Google アカウントを持ち、管理コンソールに登録された人だけが使える |
| 基盤 | AWS 東京リージョン。固定費がほぼ出ないサーバーレス構成 |
| 端末 | スマホのブラウザで撮影・登録、PC のブラウザで検索・管理 |
| 名刺の量 | 初期 1 万枚、月 1,500 枚増、3 年で 6〜7 万枚。設計上の上限は 10 万枚 |
| 見られる範囲 | 役職と部署で決まる。役員から SubMG まではすべて、EX 以下は担当部署が自分の所属と重なる名刺（§9） |

## 2. 全体構成

```text
ブラウザ（スマホ / PC）
   │
   ▼
CloudFront ─────────────┬─ /            → S3（画面。非公開バケット + OAC）
   │                    └─ /api/*       → API Gateway (HTTP API)
   │                                         │  Cognito の JWT を検証
   │                                         ├─ Lambda「app」     名刺の登録・検索・編集
   │                                         └─ Lambda「console」 管理コンソール・開発コンソール
   │
   └─ 名刺画像のアップロード / 表示は S3 の署名付き URL で直接やり取り

Lambda「app」 ──（読み取りを依頼）──▶ Lambda「scan」
   ├─ DynamoDB                          ├─ S3（画像）         読み取り
   └─ S3（画像）                         ├─ Secrets Manager   Gemini API キー（読み取りのみ）
                                        ├─ Gemini API        画像 → JSON
                                        └─ DynamoDB          結果を保存

Lambda「console」
   ├─ Cognito           無効化した人のログインの取り消し
   ├─ Secrets Manager   Gemini API キーの登録・更新（書き込み）
   ├─ DynamoDB          ユーザー・部署・モデル・プロンプト・履歴
   └─ S3（出力）         CSV を置いて署名付き URL で渡す

ログイン
ブラウザ ──▶ Cognito ──▶ Google（会社のアカウントで認証）
               │
               └─ Lambda「auth」 ──▶ DynamoDB    会社のドメインか、登録済みのアドレスかを確かめる
```

### 採用するサービスと理由

| 役割 | サービス | 理由 |
| --- | --- | --- |
| 画面の配信 | S3 + CloudFront | 固定費なし。画面と API を同じドメインにできるので CORS の設定が要らない |
| API | API Gateway HTTP API + Lambda (arm64) | 使った分だけの課金。JWT の検証を API Gateway 側に任せられる |
| 認証 | Cognito User Pool（Essentials）+ Google | Google でのログインを Cognito が受け、API Gateway がそのまま検証できるトークンを発行する。ログインの維持（トークンの更新）も Cognito に任せられる。1 万人まで無料 |
| データ | DynamoDB（オンデマンド） | 固定費なし。VPC が要らないので NAT Gateway の費用も出ない |
| 画像 | S3（非公開） | 署名付き URL でブラウザから直接アップロードし、Lambda を経由させない |
| API キー | Secrets Manager | キーの値を DB・ログ・画面に残さない。Gemini と OpenAI（議事録で使う場合）のキーを、1 つのシークレットにまとめて持つ |
| 構成管理 | Terraform | 既存プロジェクトと同じ |

### 採用しなかったもの

| 候補 | 見送った理由 |
| --- | --- |
| RDS / Aurora | SQL で検索は書きやすいが、常時稼働の固定費が出る。Lambda を VPC に入れると Gemini を呼ぶために NAT Gateway が要り、それだけで月数十ドルになる |
| EC2 1 台 + SQLite | `product-chatbot-aws` と同じ形で作れるが、月額の固定費と OS の保守が残る。この規模なら Lambda のほうが安く手間も少ない |
| OpenSearch | 検索は強力だが最小構成でも固定費が大きい。10 万件規模には過剰 |
| Cognito を使わず Google のトークンを直接使う | `meeting-bot` と同じ形で作れるが、Google のトークンは 1 時間で切れ、黙って更新できる保証が無い。ブラウザによっては 1 時間ごとに再ログインになる |
| サーバー側で Google と直接やり取りし、自前の Cookie でログインを維持する | TalentBoard と同じ方式。常時動くサーバーが前提で、ログインの維持と署名の鍵の管理を自前で作ることになる |

### 3.1 名刺を探す

```text
┌──────────────────────────────────────────────────────────┐
│ 会社名 [            ]   氏名 [            ]   [検索]       │
│                                                          │
│ ▼ その他の条件で絞る                                       │
│ ┌──────────────────────────────────────────────────────┐ │
│ │ 相手の部署名 [        ]   電話番号   [          ]      │ │
│ │ メール   [          ]   備考       [          ]        │ │
│ │ 登録者   [ 選択 ▾  ]   登録日     [    ]〜[    ]       │ │
│ │ 担当部署 (営業部) (開発部) (総務部) …                   │ │
│ └──────────────────────────────────────────────────────┘ │
│                                                          │
│ 絞り込み中: [会社名: アシスト ×] [電話番号: 03 ×]  すべて解除   │
│ 128 件                                                   │
│ ┌────┐ 株式会社アシスト  営業部                    [閲覧][編集] │
│ │写真│ 山田 太郎   03-1234-5678 / 090-...                 │
│ └────┘ yamada@example.co.jp                              │
└──────────────────────────────────────────────────────────┘
```

**検索**

- **基本は会社名と氏名。** この 2 つは常に見えている。
- **その他の条件は折りたたみ。** 開いて入力した項目だけが条件になる。会社名・氏名が空でも、その他の条件だけで検索できる。
- **複数入れたら「すべて満たす」で絞る（AND）。** 1 つの欄に空白区切りで複数語を入れた場合も AND。
- **いま効いている条件をチップで並べる。** どの条件で絞られているかが一覧の上で常に分かり、× で 1 つずつ外せる。折りたたみを閉じていても、その他の条件が効いていることを見落とさない。
- **部分一致。** 「田中」で「株式会社田中商事」も「田中 一郎」も出る。
- **表記ゆれを吸収する。** 全角 / 半角、大文字 / 小文字、ひらがな / カタカナ、氏名の間の空白を区別しない。電話番号は数字だけで比べるので、ハイフンの有無や `+81` 表記の違いは関係ない。電話番号の欄は固定電話と携帯電話の両方を探す。
- **出てくるのは、その人が見られる名刺だけ。** 役員から SubMG まではすべての名刺、EX 以下は担当部署が自分の所属と重なる名刺（§9）。件数も見られる範囲で数える。
- **「相手の部署名」と「担当部署」は別の条件。** 前者は名刺に印刷されている部署名、後者は社内でその名刺を見られる部署。担当部署の選択肢に出るのは、すべて見られる人には全部署、それ以外の人には自分の所属部署だけ。

**議事録への入口**

- 画面の下段に「議事録を作る」と「議事録の一覧」を置く。スマホでは画面の下に固定する（[minutes-design.md](./minutes-design.md) §3.1）。
- 名刺の詳細画面には「この人との議事録」を出す。出るのは、自分が見られる議事録だけ。

**検索画面からの編集**

- 一覧の各行に「編集」を置く。押すと、検索画面の上に編集パネルが開く（PC は右側、スマホは全画面）。社員B と協力会社には「編集」を出さず、行を押すと内容の表示だけが開く。
- パネルには名刺の写真と入力欄が並ぶ。写真を見ながら直せる。
- 保存すると、パネルを閉じて、その行だけを新しい内容に差し替える。検索条件、一覧の位置、ページはそのまま。
- 編集の入力欄は、登録時の確認画面・詳細画面・検索画面で同じ部品を使う。どこから直しても同じ操作になる。
- 同じ名刺を 2 人が同時に編集した場合、後から保存した人に「ほかの人が先に更新しました」と知らせ、最新の内容を見せる。黙って上書きしない。
- 入力のたびに一覧を描き直すと日本語入力の変換が壊れる（`rollplay` で実際に起きた）。検索欄と編集パネルは描き直しの範囲の外に置き、結果の一覧だけを差し替える。

**取引先ごとの表示**

検索の結果とは別に「取引先ごと」の表示を持つ。会社 → 部署 → 人の順に畳んで出し、会社名の入力で絞れる（`GET /api/companies`）。同じ会社の人が何人いて、どの部署に誰がいるかを一目で見るための表示で、検索の条件（担当部署、期間など）は効かない。

### 3.2 名刺を登録する

```text
① 読み込む          ② 待つ                ③ 表示・修正            ④ 保存
┌─────────────┐   ┌─────────────┐      ┌───────────────────┐
│ [撮影する]   │   │   ┌─────┐   │      │ ┌─────┐ 会社名 [  ] │
│ [写真を選ぶ] │ → │   │写真 │   │  →   │ │写真 │ 部署名 [  ] │ → 確認済み
│             │   │   └─────┘   │      │ └─────┘ 氏名   [  ] │
│ 裏面（任意） │   │ 読み取っています… │      │ [読み取り直す] [保存] │
└─────────────┘   └─────────────┘      └───────────────────┘
                         │ 失敗
                         ▼
                  ┌──────────────────────────┐
                  │ 読み取りに失敗しました       │
                  │ [もう一度読み取る]          │
                  │ 撮り直す ／ 手で入力する     │
                  └──────────────────────────┘
```

| 段階 | 画面 | 裏で起きていること |
| --- | --- | --- |
| ① 読み込む | 撮影、または写真を選ぶ。裏面は任意 | ブラウザ側で長辺 1,600px の JPEG に縮小し、サムネイル（320px）も作る。S3 へ直接アップロード |
| ② 待つ | 撮った写真と「読み取っています」の表示。ふつうは数秒 | 読み取りを依頼し、1.5 秒おきに状態を確かめる。60 秒を超えたら「時間がかかっています」に変える。120 秒で失敗として扱う |
| ③ 表示・修正 | 写真と、読み取り結果の入った入力欄を並べて出す。直したいところだけ直す。担当部署を確かめる | 形式がおかしいメールアドレスや、読み取れなかった項目には印を付ける |
| ④ 保存 | 「保存」で確定し、検索に出るようになる | 状態を「確認済み」にし、登録の履歴を残す |

**③ の担当部署の欄**

```text
EX、社員A、社員B、協力会社
  担当部署   [営業部 ✓] [開発部 ✓]            ← 自分の所属。兼任なら両方。外せるが 1 つは必須

MG、SubMG 以上
  担当部署   [営業部 ✓]                       ← 自分の所属
  他の部署にも見せる？   ( いいえ )  (● はい )
             (開発部 ✓) (総務部) (経理部) (企画部 ✓) (人事部)      [すべて選ぶ]
```

- 何も触らなければ、自分の所属部署がそのまま担当部署になる。続けて何枚も登録するときは、前の 1 枚で選んだ内容を引き継ぐ。
- 「他の部署にも見せる？」は、MG・SubMG 以上の人にだけ出る。選べるのは既存の部署で、ここから新しい部署は作れない。

- **失敗したときは「もう一度読み取る」ボタン 1 つで再生成する。** 同じ写真で読み取りをやり直し、② の待ち画面に戻る。撮り直しや入力のし直しは要らない。
- **保存して確認済みになった直後に、写真を攻めた縮小で置き換える。** 長辺 900px、JPEG 品質 0.4（元の 1,600px・0.85 の 300〜400KB → 50〜80KB ほど）。読み取りは元の写真で済んでいるので、保存する写真は「人が見て読める最小限」でよい。縮小はブラウザで行い、1 枚につき 1 回だけ（`imageOptimized` の印）。縮小後に「読み取り直す」をすると縮小した写真で読むので、精度が落ちることがある（画面にその旨を出す）。
- 読み取りが成功した後でも、結果がおかしければ ③ の「読み取り直す」で再生成できる。すでに手で直した項目がある場合だけ、「直した内容は置き換わります」と確かめる。
- 写真は最初にアップロードした時点で保存される。待っている間や確認の途中でブラウザを閉じても、「確認待ち」の一覧から続きができる。
- 同じメールアドレス、または同じ会社名と氏名の名刺が既にあれば、③ で知らせる。「別の名刺として登録」か「既存の名刺を更新」を選ぶ。
- 複数枚を続けて撮れる。1 枚目を待っている間に 2 枚目を撮れる。読み取りは裏で進み、確認待ちの一覧からまとめて確認する。

**既存の取引先の候補**

確認画面と編集画面で会社名を入れると、既存の名刺の会社名から似たものを候補に出す（`similarCompanies`。表記ゆれと法人格の有無を吸収）。候補を選ぶと会社名がその表記に置き換わる。目的は、同じ会社が「株式会社アシスト」「アシスト（株）」と別々に登録されて、取引先ごとの表示や議事録の検索で分かれてしまうのを防ぐこと。選ばなくても保存はできる。

### 3.3 管理コンソール

入れるのは、役員・GM・SMG と開発者。

**ユーザーの登録（1 人ずつ）**

```text
メールアドレス [                    ]
氏名           [                    ]   （任意）
部署   (営業部 ✓) (開発部 ✓) (総務部) (＋ 新しい部署)        ← 複数選べる（兼任）
                                   └→ 押すと入力欄が出て、その場で作成して選択
役職   (役員) (GM) (SMG) (MG) (SubMG) (EX) (社員A) (社員B) (協力会社) (開発者)
                                                      [登録する]
```

- 部署は既存のものをボタンで選ぶ。無ければ「＋ 新しい部署」でその場で作る。部署の作成と登録は 1 回の操作で済む。
- ここに登録されたメールアドレスの人だけが、Google でログインできる。登録されていない人は、会社の Google アカウントを持っていても入れない（§9.6）。
- パスワードも招待メールも無い。登録したら、本人にアプリの URL を伝えるだけ。
- 氏名は、登録のときに入力できる（任意）。空のままなら、本人が最初にログインしたときに Google アカウントの名前を取り込む。それまでは一覧にメールアドレスで出る。登録のときに入力した氏名があれば、そちらを優先する。
- 「開発者」のボタンは、開発者にだけ出る。
- ユーザー一覧では、部署・役職の変更と無効化ができる。状態は「未ログイン」「利用中」「無効」。
- 退職者は削除ではなく無効化。その人が登録した名刺と履歴は残る。

**ユーザーの一括登録（CSV）**

| 項目 | 仕様 |
| --- | --- |
| 列 | 部署, アドレス, 役職 の順。4 列目に氏名を書ける（任意。§13）。1 行目が見出しなら読み飛ばす |
| 兼任 | 部署の欄に `;` で区切って並べる（`営業部;開発部`）。または、同じアドレスの行を部署ごとに書く |
| 無い部署 | 新しく作る |
| 文字コード | UTF-8 と Shift_JIS を自動で見分ける。Excel で保存した CSV をそのまま使える |
| 区切り | カンマ、またはタブ |
| 上限 | 1 回 1,000 行 |
| ひな形 | 画面からダウンロードできる |

```text
① ファイルを選ぶ  →  ② 内容を確かめる（まだ何も登録されない）  →  ③ 登録する

② の画面
  読み込み結果   全 104 行
    新しく登録    96 人
    内容を変更     5 人    営業部 → 営業部;企画部 ／ 社員A → EX など、変更前と変更後を表示
    変更なし       2 人
    エラー         1 行

  新しく作る部署   3 つ
    企画部（12 人）   品質管理部（4 人）
    営業 部（1 人）   ⚠ 既にある「営業部」と似ています。書き間違いではありませんか

  エラー
    38 行目   yamada@example.com   会社のドメインではありません

  [エラーの行を除いて登録する]   [やめる]
```

- **登録の前に必ず確認画面を挟む。** 無い部署を自動で作るので、部署名の書き間違いがそのまま新しい部署になってしまう。確認画面で「新しく作る部署」を一覧にし、既存の部署と似た名前には警告を出す。
- 部署名と役職は、前後の空白、全角 / 半角、大文字 / 小文字の違いをそろえてから照合する（`submg` も `ＳｕｂＭＧ` も `SubMG`）。
- 既に登録されている人が CSV に含まれていたら、部署と役職を CSV の内容に置き換える。CSV に載っていない人には何もしない（無効化もしない）。
- エラーになる行: アドレスの形式がおかしい、会社のドメインではない、役職が一覧に無い、部署が空、同じアドレスで役職が食い違っている、開発者ではない人が「開発者」を指定した。
- 誰が・いつ・何人を登録し、どの部署を作ったかを監査ログに残す。

**部署設定**

- 追加、名前の変更、並び替え、使用停止。
- 所属ユーザーがいる部署は削除できない。使用停止にすると、ユーザーの登録や担当部署の選択肢に出なくなる。

- 行を押すと、その名刺の詳細と、その名刺だけの履歴が開く。
- 名刺の詳細画面には、全員に「登録: 佐藤 花子 2026-10-02 ／ 最終編集: 鈴木 一郎 2026-10-05」だけを出す。項目ごとの変更の中身は、管理コンソールに入れる人だけが見られる。

## 4. 名刺登録の流れ

```text
ブラウザ               Lambda「app」         Lambda「scan」        Gemini      DynamoDB
   │ 縮小・サムネイル作成     │                     │                  │            │
   │── アップロード先を要求 ─▶│                     │                  │            │
   │◀─ 署名付き URL ────────│                     │                  │            │
   │── 画像を S3 へ直接 PUT   │                     │                  │            │
   │── 読み取りを依頼 ───────▶│── 「読み取り中」で保存 ─────────────────────────────▶│
   │                        │── 読み取りを依頼 ───▶│                  │            │
   │◀─ 名刺 ID ─────────────│                     │── 画像 + プロンプト ─▶│            │
   │                        │                     │◀─ 応答 ───────────│            │
   │  （待ち画面）            │                     │  JSON を取り出す    │            │
   │                        │                     │  検証・整形         │            │
   │                        │                     │── 「確認待ち」または「失敗」で保存 ─▶│
   │── 状態を確認（1.5 秒おき）▶│── 読み出し ─────────────────────────────────────────▶│
   │◀─ 読み取り結果 ─────────│                     │                  │            │
   │ 確認・修正               │                     │                  │            │
   │── 保存 ────────────────▶│── 「確認済み」に更新、履歴を保存 ───────────────────────▶│
```

読み取りは、依頼を受ける Lambda とは別の Lambda「scan」で行う。

- API Gateway は 30 秒で応答を打ち切る。3.6〜3.8 Flash のように考える時間が長いモデルや、失敗時の自動再試行を含めると、30 秒に収まらないことがある。別の Lambda にすれば、打ち切られずに最後まで処理できる。
- ブラウザを閉じても読み取りは最後まで進み、結果は保存される。
- Gemini の API キーを読めるのは「scan」だけになる。

### 名刺の状態

| 状態 | 意味 | 検索に出るか |
| --- | --- | --- |
| 読み取り中 | Gemini の応答を待っている | 出ない |
| 確認待ち | 読み取りは済んだが、人がまだ確かめていない | 出る（印を付ける） |
| 失敗 | 読み取りに失敗した。再生成か手入力を待っている | 出ない（登録した本人の「確認待ち」一覧には出る） |
| 確認済み | 人が確かめて保存した | 出る |

## 5. Gemini 連携

### 5.1 考え方

**プロンプトは編集できる。出力の型は編集できない。**

プロンプト（読み取り方の指示）は開発コンソールから自由に書き換えられる。一方、返ってくる JSON の形は、Gemini の構造化出力の機能でコード側から指定する。

そのうえで、**Gemini の応答は「壊れているかもしれない文字列」として扱う。** 構造化出力を指定していても、前後に説明文が付く、コードブロックの記号で囲まれる、途中で切れる、といったことは起こり得る。モデルを切り替えれば振る舞いも変わる。応答から JSON を取り出す処理（§5.6）を必ず通し、取り出せなかったときは失敗として扱う（§5.7）。

### 5.2 モデル

開発コンソールの一覧から選んで切り替える。Gemini 3.8 系まで対応する。

| モデル ID | 入力 | 出力 | 思考の設定 | 補足 |
| --- | --- | --- | --- | --- |
| `gemini-3.5-flash-lite` | $0.30 | $2.50 | minimal | **初期値。** 安定版で、終了日が出ていない |
| `gemini-3.1-flash-lite` | $0.25 | $1.50 | 最も低い値 | 2027-05-07 に提供終了 |
| `gemini-3.6-flash` | $0.75 → $1.50 | $3.75 → $7.50 | minimal | 2027-01-01 に単価が 2 倍 |
| `gemini-3.7-flash` | $0.75 → $1.50 | $3.75 → $7.50 | low | 同上。minimal は使えない |
| `gemini-3.8-flash` | $0.75 → $1.50 | $3.75 → $7.50 | low | 同上。minimal は使えない |
| `gemini-3.5-flash` | $1.50 | $9.00 | 最も低い値 | |

単価は 100 万トークンあたり。2026-09-30 に公式の料金ページで確認した値。

**モデルの一覧は設定として持つ。コードに固定しない。**

Gemini は新しいモデルが毎月のように出ている（3.6 が 7 月、3.7 が 8 月、3.8 が 9 月）。モデルが出るたびにプログラムを直して配り直すのは手間なので、一覧を DynamoDB に置き、開発コンソールから追加できるようにする。

| 一覧の項目 | 内容 |
| --- | --- |
| モデル ID | Gemini に渡す名前 |
| 表示名 | 画面に出す名前 |
| 入力・出力の単価 | 概算費用の計算に使う。値上げの予定があれば、切り替わる日と新しい単価 |
| 思考の設定 | そのモデルで使える最も低い値。名刺の読み取りに深い思考は要らず、思考の分も出力として課金されるため |
| 提供終了日 | 分かっていれば。30 日前から画面に警告を出す |
| 有効 / 無効 | 無効にすると選択肢に出ない |

- **モデルの追加:** 「＋ モデルを追加」を押すと、登録済みの API キーで使えるモデルを Gemini に問い合わせ、まだ一覧に無いものを候補として出す。選んで単価を入力し、試し読みが通れば一覧に加わる。
- **試し読み:** 切り替える前に、手元の名刺画像で読み取りを試せる。結果、かかった秒数、消費トークン数が出る。
- **プレビュー版は初期の一覧に入れない。** 予告なく終了することがある（`gemini-omni-flash-preview` は 2026-09-30 に終了）。使う場合は手で追加する。
- **モデルごとの違いは 1 か所で吸収する。** 思考の設定のように、モデルによって使える値が違うものがある。呼び出しの組み立てを 1 つの部品にまとめ、一覧の設定を見て切り替える。読み取りの処理そのものは、どのモデルでも同じ。

| 共通の設定 | 内容 |
| --- | --- |
| 画像の解像度 | 既定（1 枚 1,120 トークン）。名刺は小さい文字が多いので下げない |
| 出力の上限 | 4,000 トークン。途中で切れるのを防ぐため、余裕を持たせる |
| 呼び出し方 | API キーを `x-goog-api-key` ヘッダーで渡す。キーは Lambda の中で 5 分間だけ保持する |
| 1 回の待ち時間 | 40 秒で打ち切る |

### 5.3 出力の型

| キー | 型 | 内容 |
| --- | --- | --- |
| `company` | 文字列 | 会社名 |
| `department` | 文字列 | 部署名 |
| `title` | 文字列 | 役職（例: 営業部長、代表取締役）。無ければ空文字（§13） |
| `name` | 文字列 | 氏名 |
| `phones` | 文字列の配列 | 電話番号（固定電話） |
| `mobiles` | 文字列の配列 | 携帯電話番号 |
| `emails` | 文字列の配列 | メールアドレス。複数あればすべて |

`raw_text` を残しておくと、後から項目を増やしたくなったときに、写真を読み直さずに済む。

### 5.4 プロンプトの初期値

```text
あなたは名刺の読み取り担当です。渡された名刺の画像（表面と、あれば裏面）を読み取り、指定された形式で返してください。

# 基本の決まり
- 名刺に書かれている文字だけを使います。書かれていないことを推測で補わないでください。
- 読み取れない項目、書かれていない項目は、空文字または空の配列にしてください。
- 表記は名刺のとおりに写してください。「株式会社」「(株)」などを省略したり書き換えたりしないでください。
- 日本語と英語の両方が書かれている場合は、日本語の表記を採用してください。

# 項目ごとの決まり
- company: 会社名。グループ名や親会社名が併記されている場合は、本人が所属する会社を入れ、それ以外は note に入れます。
- department: 部署名。「営業本部 第二営業部 法人課」のように階層がある場合は、名刺の順のまま空白で区切って 1 つにまとめます。役職は含めません。
- title: 役職。「営業部長」「代表取締役社長」のように、名刺に書かれているとおりに入れます。複数あれば「 / 」でつなぎます。部署名は含めません。
- name: 氏名。姓と名の間は半角の空白 1 つにします。
- name_reading: 氏名のふりがな、またはローマ字。名刺に書かれている場合だけ入れます。漢字から読みを推測しないでください。
- phones: 固定電話の番号。代表、直通など複数あればすべて入れます。FAX 番号は入れないでください。
- mobiles: 携帯電話の番号。「携帯」「Mobile」などの表示があるもの、または 070・080・090 で始まるものです。
- emails: メールアドレス。複数あればすべて入れます。
- note: 上の項目に入らない情報のうち、その人を知る手がかりになるもの。資格、所属している団体、委員などの肩書き、FAX 番号、住所、Web サイト。項目名を付けて「資格: 一級建築士 / FAX: 03-0000-0000」のように書きます。
- raw_text: 名刺に書かれている文字を、読み取れた順にすべて書き出します。

# 読み間違えやすい文字
- メールアドレスと電話番号は 1 文字ずつ確かめてください。0 と O、1 と l と I、ハイフンとアンダースコアの取り違えに注意してください。

# 返し方
- JSON だけを返してください。説明、前置き、コードブロックの記号は付けないでください。
```

役職は独立した項目（`title`）にした（2026-10-01、§13）。住所は指定の項目に無いので、初期値では備考に入れている。

### 5.5 読み取った後の処理

取り出した JSON をそのまま保存せず、サーバー側で次を行う。

- メールアドレス: 小文字にそろえ、形式を確かめる。形式がおかしいものは確認画面で印を付ける。
- 電話番号: 表示用は名刺の表記のまま。検索用に数字だけの形を別に持つ（`+81 3-1234-5678` → `0312345678`）。
- 文字数の上限を超えたものは切り詰める。
- 使ったモデル、プロンプトの版、消費トークン数、かかった秒数、試した回数を名刺ごとに記録する。

### 5.5b 同じ人の名刺と、重複の知らせ（2026-10-03 追加）

名刺の上に「人」の単位を置く。名刺 1 枚はその人の「ある時点の名刺」で、最新の 1 枚が「現在」。古い名刺は画像も内容も残り、詳細の「この人の名刺の変遷」で時系列に見られる。異動・昇進・転職の記録を失わないため。

| 判定 | 根拠 | 確認画面 |
| --- | --- | --- |
| 同じ名刺（二重登録） | 氏名と会社が同じで、電話・携帯・メール・役職もすべて同じ | 「この名刺はすでに登録されています」。既存を開くか、それでも登録するか |
| 同じ人の新しい名刺 | メールか携帯が一致、または氏名が同じで同じ取引先（`companyKey`） | 「この人の名刺があります（登録日、部署 役職）」。**「更新として登録」か「別の人として登録」を必ず選ぶ**。閲覧だけの人は「別の人」だけ |
| 同じ名前 | 氏名（正規化）だけ一致 | 小さく「同じ名前の人がいます」。既定は別の人 |

- 「更新として登録」は、新しい名刺を「現在」に、前の名刺を「過去」にする。履歴に「名刺の更新（営業部 課長 → 営業本部 部長）」を 1 件残す。前の名刺の `version` を条件にした 1 回のトランザクションで行い、同時に 2 人が更新しても片方は 409 になる。
- 保存した後からでも、詳細の「同じ人としてつなぐ」「つながりを外す」で直せる（編集できる人）。
- 議事録の「この人との議事録」と、相手の絞り込みは、人の単位でまとめる。
- 検索・一覧・取引先ごとの表示は「現在」の名刺だけ。過去の名刺は gsi1 には残すが `status` を `superseded` にして、メモリ内の索引（一覧と引き表）が落とす。gsi1 から外さないのは、warm なほかの Lambda にも差分の読み直しで「過去になった」ことが伝わるため（`updatedAt` も進める）。画面と API では `superseded` を「確認済みの過去の名刺」（`status: confirmed`、`isCurrent: false`）として見せる。

**速さとメモリ（§7 と合わせて）**

- 判定は検索用のメモリ内索引に、メール / 携帯・電話（数字だけ）/ 氏名（正規化）/ 取引先 + 氏名 の 4 つの引き表を持って O(1) で引く。全件を舐めない。鍵は文字列ではなく 30 ビットのハッシュ（整数）にし、値は 1 枚だけなら ID の文字列そのもの、2 枚目から Set にする。衝突しても候補が増えるだけで、最後に `classifyMatch` が確かめる。名刺 1 枚あたり約 150 バイト（鍵 5 個）で、6.4 万枚で約 9 MB（実測）。候補の判定は最大 50 件で打ち切る。
- 引き表に載せるのは確認待ち・確認済みの「現在」の名刺だけ。「同じ人」の相手にできるのは確認済みだけ（確認待ちは二重登録の知らせにだけ使う）。
- 一覧に過去の名刺を出す `includePast` は実装しない（索引を増やさないため）。過去の名刺は詳細の「この人の名刺の変遷」からたどる。
- 前の名刺を過去にするときは、gsi1 のキーを残したまま `status` を `superseded`、`isCurrent` を `false` にし、`updatedAt`（と gsi1 のソートキー）を進める。ほかの warm な Lambda は差分でこの項目を受け取り、`apply` が `status` を見て一覧と引き表から外す。起動時の全件読み込みも同じ判定で落とす。「現在」に戻すとき（外す、削除後の付け直し）は `status` を `confirmed` に戻し、`updatedAt` を進める。編集は過去の名刺にもできる（履歴に残す）。読み取り直しは 409。
- Cloudflare 版は D1。引き表の代わりに `idx_cards_name_n`（氏名）と `card_contacts`（メール・電話の数字 1 件 1 行。主キー `(kind, k, card_id)`）を `=` / `IN` で引く。更新は D1 の `batch`（1 トランザクション）で、`UPDATE` が 0 行だったときは `json('!')` で意図的にエラーにして全体を巻き戻す。
- 過去の名刺はメモリ内の索引に載せないので、人の名刺が増えても検索の速さとメモリは変わらない（起動時の読み込みは gsi1 に残る過去の名刺の分だけ増える）。
- 人ごとの名刺の一覧は `PERSON#<人ID>` / `CARD#<名刺ID>` の小さな項目で引く（Query 1 回）。検索を経由しない。
- 更新は DynamoDB の TransactWrite 1 回（新しい名刺の put、前の名刺の update、履歴の put、人の項目の put）。読み直しは不要で、応答は書いた内容から作る。

### 5.6 応答から JSON を取り出す

応答の文字列に、上から順に次の手当てをする。取り出せた時点で終わる。

| 順 | 手当て | 対応できる応答の例 |
| --- | --- | --- |
| 1 | そのまま JSON として読む | `{"company": "…"}` |
| 2 | 見えない文字（BOM、ゼロ幅の空白）と、前後のコードブロックの記号を取る | ` ```json ` で始まり ` ``` ` で終わる |
| 3 | 最初の `{` から、対応する `}` までを切り出す | `読み取り結果は以下です。{…} ご確認ください。` |
| 4 | よくある崩れを直してから読む | 下の表 |
| 5 | 途中で切れている場合は、開いたままの文字列と括弧を閉じて、読めた項目だけを拾う | `{"company": "株式会社アシスト", "name": "山田` |

3 の切り出しは、文字列の中かどうかを見ながら 1 文字ずつ数える。備考に `}` や `{` が書かれていても、そこで切らない。

**4 で直す崩れ**

| 崩れ | 例 | 直し方 |
| --- | --- | --- |
| コメント | `"name": "山田 太郎", // 氏名` | 文字列の外にある `//` と `/* */` を消す |
| 最後の余分なカンマ | `["a@example.jp",]` | 消す |
| 全角の記号、飾りの引用符 | `“company”：“…”` | 文字列の外にあるものだけ半角にする |
| キーに引用符が無い、一重引用符 | `{company: '…'}` | 二重引用符にする |
| 文字列の中の生の改行 | 住所の途中で改行されている | `\n` にする |

**取り出した後に形をそろえる**

| ずれ | 例 | そろえ方 |
| --- | --- | --- |
| 配列のはずが文字列 | `"emails": "a@example.jp"` | 1 件の配列にする。`,` `;` `/` で区切られていれば分ける |
| 文字列のはずが配列や `null` | `"company": null` | 空文字にする。配列なら空白でつなぐ |
| キーの名前が違う | `email` `mail` `tel` `会社名` | 決めてある別名の表で、正しいキーに読み替える |
| 外側が 1 つ多い | `{"result": {…}}` `[{…}]` | 中身を取り出す |
| 知らないキー | `"fax": "…"` | 捨てる（備考に入れたい内容はプロンプトで指示する） |

- 手当てをして取り出した場合は、どの手当てが効いたかを記録する。特定のモデルやプロンプトで崩れが増えたら、開発コンソールの利用状況で分かる。
- この処理は Gemini を呼ばずに試せるので、崩れた応答の見本を集めてテストにする。新しい崩れ方が見つかったら、見本を足してから直す。

### 5.7 失敗したとき

**自動で試し直すもの**（利用者には待ち画面のまま）

| 状況 | 動作 |
| --- | --- |
| 混雑、一時的なエラー（429、5xx、時間切れ） | 間隔を空けて 2 回まで |
| JSON を取り出せなかった、主な項目がすべて空だった | 1 回だけ |

**それでも失敗したとき**

| 種類 | 画面の文言 | ボタン |
| --- | --- | --- |
| 応答が壊れていた | 読み取り結果を受け取れませんでした | **[もう一度読み取る]** |
| 応答が途中で切れた | 読み取りが途中で止まりました | **[もう一度読み取る]**（読めた項目は表示する） |
| 混雑・時間切れ | 混み合っていて読み取れませんでした | **[もう一度読み取る]** |
| 項目がすべて空 | 名刺の文字を読み取れませんでした | **[もう一度読み取る]**　撮り直す ／ 手で入力する |
| 応答が拒否された | この写真は読み取れませんでした | 撮り直す ／ 手で入力する |
| API キーが無効、モデルが使えない | 設定に問題があります。開発者に連絡してください | 手で入力する |

- 再生成で直る見込みがあるものだけに「もう一度読み取る」を出す。API キーが無効な場合のように、何度やっても同じ結果になるものには出さず、開発コンソールに警告を出す。
- どの失敗でも、写真は保存されている。「手で入力する」を選べば、写真を見ながら入力して登録できる。
- 失敗した応答の文字列は、原因を調べるために 30 日だけ残す。開発コンソールからだけ見られる。
- 1 人あたりの読み取り回数に 1 日の上限（初期値 200 回、再生成を含む）を設け、誤操作や不正利用で費用が膨らむのを防ぐ。

**履歴の種類**

| type | 残すとき | `changes` の中身 |
| --- | --- | --- |

| 読み取り直し | 再生成した | 成功か失敗か、失敗の種類 |
| 削除・復元 | 削除した、元に戻した | なし |

内容が変わっていない保存は、履歴に残さない。

**索引**

| 索引 | キー | 用途 |
| --- | --- | --- |
| `gsi1` | `IDX#<0〜7>` / `<updatedAt>#<名刺ID>` | 検索用の一覧。検索と一覧表示に使う項目だけを含める |
| `gsi2` | `HIST#<年月>` / `<日時>#<名刺ID>` | 管理コンソールの履歴と、履歴の CSV。月ごとに新しい順で読める |

- 名刺の削除は `deletedAt` を入れる論理削除。30 日後に画像ごと実削除する。誤って消した場合に戻せる。
- 名刺を実削除するときは、その名刺の履歴も消す（変更前後の値に個人情報が含まれるため）。「誰がいつ削除したか」だけは監査ログに残る。
- 部署名を変えても、ユーザーと名刺は部署 ID で持っているので書き換えが要らない。
- ユーザーはメールアドレスをキーにする。ログインする前に登録しておく必要があり、その時点では Google 側の ID が分からないため。最初のログインで Google 側の ID を記録し、以後はメールアドレスと ID の両方が一致することを確かめる。
- 検索用の一覧（`gsi1`）には担当部署も含める。検索のとき、メモリの中で「その人に見える名刺」に絞ってから条件を当てる。
- 所属するユーザーがいる部署、担当部署として名刺に付いている部署は、削除できない。使用停止にすると、登録や割り当ての選択肢に出なくなる（既に付いている分はそのまま）。

## 7. 検索の仕組み

DynamoDB は部分一致の検索が苦手で、条件に合うものを探すには全件を読むことになる。検索のたびに全件を読むと、件数が増えるほど遅く、高くなる。

そこで、**検索用の軽い一覧を Lambda のメモリに持ち、検索はメモリの中で行う**。`rollplay` で使っている方式と同じ考え方。

1. Lambda の起動時に、`gsi1` から検索用の項目だけを全件読み込む。8 分割を並行して読むので、10 万件でも 1〜2 秒。
2. 検索のたびに、前回読んだ時刻より後に更新された名刺だけを `gsi1` から取り込む（更新が無ければ読み取りは最小単位で済む）。
3. メモリ上の一覧を条件で絞り、並べ替えて、1 ページ分を返す。

- 検索そのものは数十ミリ秒。どの項目の組み合わせでも同じ速さ。
- 検索用の一覧は 1 件 800 バイトほど。10 万件で 80MB、メモリ上に展開しても 200〜300MB で、Lambda のメモリ 1GB に収まる。
- 登録・更新した名刺は、次の検索から結果に出る（索引への反映に 1 秒ほどかかることがある）。検索画面から編集した行は、保存の応答で返ってきた内容にその場で差し替えるので、反映を待たない。
- 10 万件を大きく超える場合は、この部分だけを全文検索の仕組みに置き換える。名刺のデータと API の形は変えずに済む。

## 9. 権限

### 9.1 役職と、できること

| 段階 | 役職 | 見られる名刺 | 登録 | 編集 | 他の部署にも見せる | 管理コンソール | 開発コンソール |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 開発 | 開発者 | すべて | ○ | ○ | ○ | ○ | ○ |
| 全社管理 | 役員、GM、SMG | すべて | ○ | ○ | ○ | ○ | － |
| 全社編集 | MG、SubMG | すべて | ○ | ○ | ○ | － | － |
| 部署編集 | EX、社員A | 担当部署が自分の所属と重なるもの | ○ | ○ | － | － | － |
| 部署閲覧 | 社員B、協力会社 | 担当部署が自分の所属と重なるもの | ○ | － | － | － | － |

- 登録は全員ができる。
- 権限の段階は 5 つで固定。どの役職がどの段階に当たるかは設定として持ち、開発コンソールから変えられる。役職が増えたり名前が変わったりしても、プログラムを直さずに済む。
- 1 人の役職は 1 つ。部署は複数持てる（兼任）。

### 9.2 担当部署

名刺ごとに「担当部署」を持つ。**担当部署は、その名刺を見られる部署のこと。** 名刺に印刷されている相手の部署名とは別のもの。

| 登録する人 | 担当部署の決まり方 |
| --- | --- |
| EX、社員A、社員B、協力会社 | 自分の所属部署。兼任している場合は所属がすべて選ばれた状態で出て、外すこともできる（1 つは必須）。所属以外の部署は選べない |
| MG、SubMG 以上 | 自分の所属部署が選ばれた状態で出る。「他の部署にも見せる？」を「はい」にすると、既存の部署から複数選べる |

- 部署編集・部署閲覧の人に見えるのは、名刺の担当部署と自分の所属部署が 1 つでも重なる名刺だけ。
- 兼任している人は、どちらの部署の名刺も見える。
- 見える範囲は担当部署だけで決まる。自分が登録した名刺でも、異動して所属が変わると見えなくなる（§13）。
- 登録後に担当部署を変えられるのは、編集できる人だけ。部署編集の人は自分の所属の範囲で、全社編集以上の人はすべての部署から選べる。担当部署の変更も履歴に残る。

| 「開発者」の役職を付ける・外す | － | － | － | － | ○ |
| API キー、モデル、プロンプト、CSV 出力 | － | － | － | － | ○ |

- 部署閲覧の人も、登録の途中では読み取り結果を直せる。直せないのは、保存した後。
- 削除は開発のみ（誤削除の防止）。登録の途中（保存前）の自分の下書きを取りやめるのだけは、本人ができる。
- 全社管理の人が自分を「開発者」に変えることはできない。
- 最後の 1 人の開発者と、最後の 1 人の管理コンソールに入れる人は、無効化も役職の変更もできないようにする。

### 9.4 守り方

- **判定はすべてサーバー側で行う。** 画面側でボタンやメニューを隠すのは見た目だけで、守りにはしない。
- 見える範囲の判定は、検索だけでなく、詳細、画像の URL の発行、読み取りの状態、編集、再生成、履歴のすべてで行う。名刺 ID を直接指定しても、見える範囲の外なら「見つかりません」を返す。
- 登録時の「同じ名刺が既にあります」の知らせは、その人に見える範囲の名刺だけを対象にする。範囲の外の名刺の存在が、知らせを通じて漏れないようにする。
- 役職と所属部署は、リクエストのたびに DynamoDB のユーザー情報から読む（Lambda の中で 60 秒だけ保持）。役職の変更や無効化は、1 分以内にすべての操作に効く。

### 9.5 Lambda に与える権限

Lambda を分けているのは、権限を絞るため。

| Lambda | 与える権限 |
| --- | --- |
| app | DynamoDB の読み書き、画像バケットの読み書き、「scan」の呼び出し |
| scan | DynamoDB の読み書き、画像バケットの読み取り、API キーの**読み取り** |
| console | DynamoDB の読み書き、Cognito のユーザーの無効化とログインの取り消し、API キーの**書き込み**、出力バケットへの書き込み、「scan」の呼び出し |
| auth | DynamoDB のユーザー情報の読み取りと、ログイン日時の記録 |

### 9.6 ログイン

**Google でログインする。会社の組織内のアカウントで、かつ管理コンソールに登録されている人だけが入れる。** パスワードはアプリ側に持たない。

関門は 3 つ。どれか 1 つでも通らなければ入れない。

| 関門 | どこで | 何を確かめるか | 確かめる時 |
| --- | --- | --- | --- |
| 1 | Google | 会社の組織のアカウントか。OAuth 同意画面のユーザーの種類を「内部」にすると、組織の外のアカウントは Google が拒否する | ログインのたび |
| 2 | Cognito（Lambda「auth」） | Google が発行した証明（ID トークン）の `hd` が会社のドメインと一致するか。メールアドレスが管理コンソールに登録されていて、無効になっていないか | ログインのたび |
| 3 | API（Lambda「app」「console」） | リクエストのたびに、ユーザー情報を DynamoDB から読み、登録の有無・無効・役職・所属部署を確かめる | すべての操作 |

- **関門 1 だけに頼らない。** TalentBoard は、アプリ側では登録の有無しか確かめておらず、組織内かどうかは Google 側の設定に任せていた。設定が「外部」に変わると、気付かないまま組織の外のアカウントが関門 1 を通るようになる。関門 2 で `hd` を確かめておけば、その場合も止まる。`hd` の確かめ方は `bnew_chat_pj` と同じ（`hd` が無い、または会社のドメインと違えば拒否）。
- **本当に守っているのは関門 3。** 関門 1 と 2 はログインの時しか働かない。ログインした後で無効にされた人や役職が変わった人は、関門 3 で 1 分以内に反映される。
- 登録されていない人がログインしようとすると、「このアカウントは登録されていません。管理者に連絡してください。」と出る。名刺の情報には一切触れられない。

**ログインの流れ**

```text
ブラウザ             Cognito                Google              Lambda「auth」
   │── ログイン ──────▶│                      │                      │
   │                  │── そのまま Google へ ─▶│                      │
   │                  │                      │ 会社のアカウントで認証   │
   │                  │◀─ 証明（ID トークン）──│                      │
   │                  │── 証明の中身を渡す ──────────────────────────▶│
   │                  │                      │      hd を確かめる      │
   │                  │                      │      登録済みか確かめる  │
   │                  │◀─ 通す ／ 拒否 ───────────────────────────────│
   │◀─ トークン ───────│                      │                      │
```

| 項目 | 設定 |
| --- | --- |
| Cognito のログイン画面 | 出さない。アプリの「Google でログイン」から、そのまま Google へ進む |
| アプリが受け付けるログイン方法 | Google だけ。パスワードでのログインと、利用者自身によるアカウント作成は無効 |
| Google の連携の種類 | ソーシャル（Google）。汎用の OIDC として設定すると、料金の区分が変わり無料の枠が 50 人になる |
| ログインの維持 | 30 日。その間は、開き直しても再ログインは要らない（§13） |
| トークンの有効期限 | 1 時間。切れる前にアプリが黙って更新する |
| 無効にしたとき | DynamoDB の状態を「無効」にする（関門 3 が 1 分以内に効く）。同時に、Cognito 側でもその人を無効にし、ログインの維持を取り消す |
| 最初の 1 人 | Terraform の変数で、最初の開発者のメールアドレスを登録する。その人がログインして、ほかの人を登録する |
| Google の OAuth クライアントの秘密の値 | Terraform に変数で渡す。リポジトリには入れず、GitHub Actions の Secrets に置く |

**Lambda「auth」が呼ばれる時**

| 時 | 確かめること |
| --- | --- |
| Google から戻ってきた直後（毎回） | `hd` が会社のドメインと一致するか |
| 初めてのログイン | メールアドレスが登録済みで、無効でないか。通ったら Google 側の ID を記録する |
| 2 回目以降のログイン | 同じ。加えて、記録してある Google 側の ID と一致するか |

**実機で確かめること**

公式の資料だけでは確定できなかったので、段階 1 の最初に確かめる。

| 確かめること | うまくいかない場合 |
| --- | --- |
| Cognito が渡してくる証明の中身に `hd` が含まれるか | 関門 2 の `hd` の確認を、メールアドレスのドメインの確認に置き換える。関門 1 と 3 はそのまま |
| Lambda「auth」が拒否したとき、アプリに戻ってくる情報の形 | 「登録されていません」の案内を出す条件を、戻ってくる形に合わせる |
| Google 側で「内部」にできるか（Google Cloud のプロジェクトが会社の組織に属している必要がある） | 組織に属するプロジェクトを作り直す |

## 10. CSV 出力

開発コンソールから、2 種類を出せる。

### 10.1 名刺の一覧（名刺 1 枚が 1 行）

| 分類 | 列 |
| --- | --- |
| 内容 | 会社名, 部署名, 役職, 氏名, 氏名の読み, 電話番号, 携帯電話番号, メールアドレス, 備考 |
| 担当部署 | 担当部署（複数あれば `;` で区切る） |
| 登録 | 登録者, 登録者の部署, 登録者の役職, 登録日時 |
| 編集 | 最終編集者, 最終編集日時, 編集回数, 編集履歴 |
| 読み取り | 読み取り回数, 読み取りに使ったモデル |
| その他 | 状態, 名刺ID |

「編集履歴」の列には、その名刺の編集を古い順に 1 つのセルにまとめる。

```text
2026-10-02 14:03 佐藤 花子: 電話番号, 部署名 / 2026-10-05 09:12 鈴木 一郎: メールアドレス
```

変更前後の値までは入れない。1 つのセルに収まらなくなるため。値が要るときは履歴の CSV を使う。

### 10.2 履歴（変更 1 件が 1 行）

| 列 |
| --- |
| 日時, 種類, 操作した人, 操作した人の部署, 編集した画面, 名刺ID, 会社名, 氏名, 変更した項目, 変更前, 変更後 |

1 回の編集で 2 つの項目を変えた場合は 2 行になる。登録や削除のように項目の変更が無いものは、変更した項目以降を空にして 1 行。

### 10.3 共通の仕様

| 項目 | 仕様 |
| --- | --- |
| 文字コード | UTF-8（BOM 付き）。Excel でそのまま開ける |
| 複数の値 | 電話番号・メールアドレスが複数ある場合は `;` で区切って 1 つのセルに入れる |
| 範囲 | 全件、または条件で絞り込み（名刺は検索と同じ条件、履歴は期間・種類・操作した人） |
| 受け渡し | S3 に作成し、5 分だけ有効な URL でダウンロード。ファイルは 1 日で自動削除 |
| 記録 | 誰が・いつ・どの種類を・何件出力したかを監査ログに残す |

- `=` `+` `-` `@` で始まるセルは、Excel で数式として実行されないように処理する。`+81` で始まる電話番号もこれに当たるので、値は変えずに文字列として扱われる形にする。
- Lambda の応答には 6MB の上限があるので、CSV を応答に直接載せず S3 経由にする。

## 11. セキュリティと個人情報

名刺は個人情報なので、次を前提にする。

- **Gemini API は有料枠で使う。** 無料枠は入力が Google 側の改善に使われ得る。詳細は [cost-estimate.md](./cost-estimate.md)。
- API キーは Secrets Manager だけに置く。DynamoDB、ログ、画面、API の応答には出さない。Terraform は値の入っていない入れ物だけを作り、値は開発コンソールから入れる。
- API キーには、Google 側で「Gemini API だけに使える」制限を付ける。IP アドレスでの制限は使えない（Lambda は送信元の IP が固定されない）。
- 名刺の内容、Gemini の応答、API キーを CloudWatch のログに書かない。ログには件数や所要時間などの数値だけを残す。失敗した応答は DynamoDB に 30 日だけ置き、開発者だけが見られる。
- 履歴には変更前後の値が入る。見られるのは管理コンソールに入れる人だけで、名刺を実削除するときに一緒に消す。
- 画像は非公開バケット。表示用の URL は有効期限付き。
- ログインは Google だけ。会社の組織内のアカウントで、かつ管理コンソールに登録された人だけが使える（§9.6）。パスワードはアプリ側に持たない。2 段階認証は Google Workspace 側の設定に従う。
- 見られる範囲と編集の可否は、役職と担当部署からサーバー側で判定する（§9.4）。
- 監査ログに残す操作: CSV 出力、名刺の削除、ユーザーの登録・一括登録・無効化・役職や部署の変更、部署の作成、拒否されたログイン、API キーの更新、プロンプト・モデル・役職の設定の変更。
- 社内からのアクセスだけに絞る場合は、CloudFront に IP 制限を付ける（§13）。
- 画面に出す値はすべてエスケープする。名刺から読み取った文字列は外部から来た値として扱う。

## 14. 開発の進め方（案）

| 段階 | 内容 |
